# План подготовки: Golang Developer @ Umbrella

Вакансия: [vacancy.md](./vacancy.md). Профиль — SIEM-платформа: сбор и обработка
телеметрии (NetFlow/IPFIX/Syslog/Kafka → ClickHouse) с упором на PPS/EPS,
latency и память. План не учит Go с нуля — ты уже senior — он закрывает **специфику вакансии**: сетевые протоколы,
высокий PPS, профилирование под
нагрузкой и то, как это подтвердить на собеседовании и в портфолио.

Отмечай `- [x]` по мере прохождения.

## Порядок реализации капстоуна (M0–M14)

Этапы 0–9 ниже сгруппированы **по темам** (конкурентность, производительность,
протоколы...) — это справочник, что нужно изучить. Но если писать капстоун-
проект в этом же порядке, получится гора недописанных абстракций: сначала
абстрактный worker pool без данных, которые через него текут, потом
парсер, который некуда передать, и так далее.

Таблица ниже — **порядок, в котором стоит писать код**: вертикальными
срезами. Каждый шаг добавляет вертикальный кусок реального пайплайна (`ingestion → parsing → enrichment → storage`),
который сразу собирается,
проходит `go test -race` и что-то делает end-to-end — а не лежит
недописанным до "потом". Темы из Этапов 1–7 при этом никуда не деваются —
они просто прикладываются к конкретному шагу M-таблицы в тот момент, когда
он их требует (например, тема "profiling" из Этапа 2 применяется на шаге M9,
когда уже есть что профилировать).

Колонка "Пакеты" — это каталоги в скелете проекта (`internal/...`), которые
сейчас содержат только `doc.go` с описанием назначения: код там пишешь ты
сам, шаг за шагом по этой таблице.

| #       | Что делаешь                                      | Пакеты (пишешь сам)                                                                     | Definition of Done                                                                                                 |
|---------|--------------------------------------------------|-----------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| **M0**  | Разобраться в каркасе, который уже есть          | читаешь `cmd/collector`, `internal/config`, `internal/server`, `internal/observability` | можешь пересказать, как работает graceful shutdown, не подсматривая                                                |
| **M1**  | Парсер **NetFlow v5** — первый вертикальный срез | `internal/netflow/v5.go`                                                                | table-driven тесты + фикстуры в `test/testdata/netflow`, бенчмарк записан в `docs/benchmarks.md`                   |
| **M2**  | UDP-приёмник                                     | `internal/ingest`                                                                       | `loadgen` → collector реально принимает пакеты; `SO_RCVBUF`, backpressure (drop+метрика при переполнении канала)   |
| **M3**  | Worker pool / fan-in, подключаем парсер          | `internal/pipeline`                                                                     | `go test -race` и `goleak` чистые; graceful shutdown дожидается воркеров                                           |
| **M4**  | Storage-заглушка, замыкаем пайплайн end-to-end   | реализация `storage.Storage` (лог/in-memory)                                            | `loadgen → ingest → parse → storage` работает целиком, видно в логах                                               |
| **M5**  | **NetFlow v9 / IPFIX** — темплейты               | `internal/netflow` (v9), `internal/ipfix`                                               | edge case "data record раньше темплейта" покрыт тестом                                                             |
| **M6**  | **Syslog RFC 5424 + CEF**                        | `internal/syslog`, `internal/cef`                                                       | fuzz-корпус засеян, `go test -fuzz` не падает                                                                      |
| **M7**  | Реальный storage — **ClickHouse batch insert**   | `internal/storage/clickhouse`                                                           | батчинг по size-or-timeout через `select`+таймер (без `time.Sleep`)                                                |
| **M8**  | **Kafka** producer/consumer                      | `internal/storage/kafka`                                                                | consumer group, graceful shutdown по `context`                                                                     |
| **M9**  | Performance-проход по всему пайплайну            | правки в `netflow`/`ingest`/`pipeline`                                                  | `pprof` под нагрузкой `loadgen`, минимум 2 оптимизации с `benchstat` в `docs/benchmarks.md`                        |
| **M10** | Наблюдаемость                                    | `internal/observability` (metrics)                                                      | Prometheus-метрики PPS/EPS, p95/p99, размер очередей — видно через `/metrics`                                      |
| **M11** | Сборка и поставка                                | `deploy/`                                                                               | статический бинарник, cross-compile, размер docker-образа задокументирован, systemd-юнит реально стартует          |
| **M12** | TLS/mTLS + auth (если делаешь REST/gRPC API)     | `internal/server` / `api/proto`                                                         | mTLS между сервисами, JWT-проверка на API                                                                          |
| **M13** | CI benchmark-gate                                | `.github/workflows/ci.yml`                                                              | CI падает при регрессии `benchstat` относительно baseline                                                          |
| **M14** | Финальная полировка портфолио и интервью         | `README.md`, `docs/architecture.md`                                                     | цифры в README настоящие (не придуманные), 2–3 истории "production incident" подкреплены реальными профилями из M9 |

Практика на каждом шаге одна и та же: пишешь логику → `go test -race
-count=1 ./...` → коммит. Не переходи к следующему M, пока предыдущий не
проходит тесты и не запускается end-to-end — иначе накопится тот же долг
недописанных абстракций, которого эта таблица призвана избежать.

## Этап 0 — Самооценка (0.5 дня)

- [ ] Пройтись по разделу "Требования" в `vacancy.md` и честно отметить для себя
  3 самых слабых пункта — на них уйдёт основное время, остальное — повторение.
- [ ] Завести отдельный репозиторий/папку под капстоун-проект (см. Этап 8) —
  именно он станет твоим ответом на "ссылку на GitHub с примерами кода".
- [ ] Составить список из 3–5 реальных production-историй из своего опыта,
  которые ложатся на обязанности вакансии (см. Этап 9) — их удобнее
  вспоминать заранее, чем на созвоне.

## Этап 1 — Конкурентность и рантайм Go (2–3 дня)

- [ ] Worker pool / fan-in / fan-out / backpressure / bounded queues — написать
  или освежить эталонную реализацию. Уметь обосновать: как выбрана ёмкость
  буфера канала, как считается число воркеров, как их выбор влияет на
  PPS/EPS.
- [ ] Утечки горутин: типовые причины (забытый `<-ctx.Done()`, канал без
  читателя/писателя, недостижимый `select`) и диагностика через
  `runtime.NumGoroutine()`, goroutine dump, `go.uber.org/goleak` в тестах.
- [ ] Deadlock/race диагностика: уметь по выводу `go test -race` и по
  goroutine dump локализовать проблему за минуты, а не полчаса.
- [ ] `context`: cancellation/deadline propagation через несколько уровней
  вызовов, `context.WithTimeout` + graceful shutdown по сигналу.
- [ ] `sync.Once`, `errgroup`, `singleflight` — знать сигнатуры и один
  реальный кейс применения каждого (например, singleflight для
  дедупликации одинаковых enrichment-запросов).
- [ ] Go memory model / happens-before — устно сформулировать 2–3 примера,
  где неправильное предположение о happens-before ломает код без видимой
  гонки в `-race` (например, порядок публикации указателя без синхронизации).

## Этап 2 — Производительность и профилирование (3–4 дня)

Вакансия явно проверяет измеримые "было/стало" результаты — без цифр ответ не
засчитают.

- [ ] Escape analysis: прогнать `-gcflags="-m"` на своём коде, найти и убрать
  минимум одну лишнюю аллокацию (передача по указателю не туда, где не
  нужно; конкатенация строк вместо `strings.Builder`).
- [ ] `sync.Pool` + переиспользование буферов — применить в парсере из Этапа 3
  и замерить `benchstat` до/после.
- [ ] GC-тюнинг: `GOGC`/`GOMEMLIMIT`, прогнать сервис под `GODEBUG=gctrace=1`,
  уметь прочитать строку трейса.
- [ ] `GOMAXPROCS` в контейнерах/cgroups — знать про `automaxprocs` и почему
  это важно для сервисов с высоким PPS в k8s/systemd.
- [ ] `pprof`: снять CPU и heap профиль под нагрузкой, построить flame graph,
  объяснить hot path.
- [ ] `runtime/trace` + `go tool trace` — отдельно от pprof, посмотреть
  планировщик под нагрузкой (goroutine blocking, syscalls).
- [ ] `benchstat`: написать `testing.B` бенчмарк и сравнить два варианта
  реализации (например, `bufio.Scanner` vs `encoding/binary` напрямую в
  `[]byte`).
- [ ] Zero-copy: осознанно применить `[]byte` вместо `string` в одном парсере
  и объяснить, где именно это экономит копирование.

## Этап 3 — Протоколы и сетевой стек (4–5 дней, ядро вакансии)

Это то, чего в общем Go-собеседовании обычно нет — специфика SIEM/NetFlow.
Наибольший ROI — написать хотя бы один парсер целиком.

- [ ] Изучить формат **NetFlow v5** (фиксированный бинарный заголовок + записи) —
  написать парсер `[]byte → struct` через `encoding/binary`, с
  table-driven тестами на валидные/битые пакеты.
- [ ] Изучить **NetFlow v9 / IPFIX** — темплейт-based формат (в отличие от v5),
  уметь объяснить проблему разбора без знания темплейта заранее и как её
  решают (кэш темплейтов по `(exporter, template ID)`).
- [ ] **Syslog RFC 5424** — написать парсер текстового формата (заголовок +
  structured data), включая edge cases (частичные сообщения по TCP,
  разделение по `\n` при чтении из UDP/TCP сокета).
- [ ] **CEF (Common Event Format)** — разобраться в структуре, написать хотя бы
  парсер заголовка, чтобы на словах уверенно сравнить с Syslog/IPFIX.
- [ ] Собрать мини-пайплайн `ingestion → parsing → enrichment → storage` —
  это ключевая фраза из вакансии, дословно, будет на собеседовании.
  Компоненты: приёмник по UDP → worker pool парсеров → канал в
  enrichment → батчинг в "storage" (можно заглушка).
- [ ] Высокий PPS без потерь пакетов: изучить `SO_REUSEPORT` (несколько
  слушателей на один порт), настройку `rmem`/`SO_RCVBUF`, batch reading (`recvmmsg` или буферизация через собственный
  ring buffer).
  Явно продумать backpressure: что происходит с пакетами при переполнении
  очереди (drop с метрикой, не блокировка ридера).
- [ ] (Опционально, "будет преимуществом") `gopacket`/`AF_PACKET`/PCAP —
  прочитать пакет из `.pcap` файла и распарсить IP/UDP заголовок вручную,
  чтобы на словах ориентироваться в теме, даже без глубокого опыта.

## Этап 4 — Инфраструктура данных (2–3 дня)

- [ ] **Kafka**: consumer group, at-least-once vs exactly-once, backpressure
  при медленном consumer'е. Написать мини-consumer с graceful shutdown по
  `context`.
- [ ] **ClickHouse**: batch insert (почему построчные INSERT — антипаттерн),
  выбор движка таблицы (MergeTree family) под event-данные, партиционирование
  по времени. Написать пример батчинга: копим N записей или таймаут — что
  наступит раньше (через `select` с таймером, без `time.Sleep`).
- [ ] **Redis**: типовое применение в этом контексте — дедупликация событий,
  rate limiting, кэш темплейтов IPFIX.
- [ ] **TLS/mTLS, X.509**: настроить mTLS между двумя демо-сервисами (`crypto/tls`,
  `tls.Config{ClientAuth: tls.RequireAndVerifyClientCert}`).
- [ ] **OAuth2/OIDC/JWT**: освежить разницу между ними и где каждый уместен
  для защиты REST/gRPC API коллектора.

## Этап 5 — Сборка и поставка (1–2 дня)

- [ ] Собрать статический бинарник: `CGO_ENABLED=0 go build`, проверить
  `file`/`ldd` на результат.
- [ ] Cross-compilation: собрать под `GOOS=linux GOARCH=amd64` и `arm64`.
- [ ] Versioning через `-ldflags "-X main.version=..."`, build tags для
  dev/prod вариантов сборки.
- [ ] Минимальный Docker-образ (`distroless` или `scratch`), сравнить размер
  образа до/после.
- [ ] Написать `.service`-юнит для systemd: `ExecStart`, `Restart=on-failure`,
  `LimitNOFILE` (актуально для высокого PPS — лимит файловых дескрипторов/
  сокетов).
- [ ] Graceful shutdown: `os/signal.NotifyContext` + таймаут на дожидание
  воркеров — без `time.Sleep`, через `context` и `sync.WaitGroup`.

## Этап 6 — Тестирование и CI-дисциплина (1–2 дня)

- [ ] Table-driven тесты через `testify/require` для одного из парсеров (Этап 3) — включая edge cases: пустой ввод,
  битый заголовок, обрезанный
  пакет.
- [ ] Fuzzing: `go test -fuzz` на бинарном парсере (NetFlow/IPFIX) — прямое
  требование вакансии и хорошо ловит панику на некорректном вводе.
- [ ] `golangci-lint run` на своём коде, поправить реальные замечания.
- [ ] `go test -race -count=1 ./...` — обязательный прогон конкурентных
  пакетов.
- [ ] Продумать "benchmark-gate" в CI на словах: как зафиксировать
  performance-регрессию бенчмарком (baseline + `benchstat` diff + порог).

## Этап 7 — Наблюдаемость (1 день)

- [ ] `log/slog`: структурированное логирование (уровни, контекстные поля:
  exporter IP, template ID, PPS текущего окна).
- [ ] `client_golang` (Prometheus): счётчики/гистограммы для PPS/EPS, p95/p99
  latency, размер очередей enrichment/storage.
- [ ] `net/http/pprof` подключить за отдельным портом/флагом (не в публичный
  listener).
- [ ] (Опционально) OpenTelemetry трейсинг одного запроса через
  `ingestion → parsing → enrichment → storage`.

## Этап 8 — Капстоун-проект для портфолио (обязательное требование вакансии)

Вакансия прямо требует "ссылку на GitHub/GitLab с примерами кода: сервисы,
парсеры, benchmarks". Материалы этапов 1–7 нужно собрать в один презентабельный
репозиторий/README, а не оставлять разрозненными демками.

- [ ] Собрать мини-NetFlow/IPFIX collector: приёмник по UDP → парсер → worker
  pool → батчинг → запись (в ClickHouse или в интерфейс-заглушку с реальной
  имплементацией под ClickHouse).
- [ ] Добавить `testing.B` бенчмарки на hot path (парсинг, батчинг) и
  закоммитить `benchstat`-сравнение "было/стало" хотя бы для одной
  оптимизации — это именно то, что просят на собеседовании.
- [ ] README с архитектурной схемой пайплайна и цифрами (PPS, allocations/op,
  p95 latency) — HR и техлид смотрят на GitHub до звонка.
- [ ] Убедиться, что `go vet`, `golangci-lint`, `go test -race` проходят на
  чистом клоне — это будет первое, что проверят.

## Этап 9 — Подготовка к самому собеседованию (1 день)

- [ ] Подготовить 2–3 истории "diagnosed production incident" по требованиям
  вакансии: потеря пакетов, утечка горутин, деградация performance, рост
  очередей — с конкретными метриками/профилями, не абстрактно.
- [ ] Подготовить структуру ответа на промпт-инжиниринговые вопросы про AI-
  инструменты (раз вакансия их упоминает): контекст → задача → контракт (сигнатура) → вход/выход → ограничения → edge
  cases → критерии приёмки.
- [ ] Подготовить вопросы работодателю: текущий PPS/EPS в проде, объём данных
  в сутки, как устроен CI benchmark-gate сейчас, стек мониторинга (Prometheus/Grafana уже есть или предстоит внедрять).
- [ ] Ежедневный status report упомянут в обязанностях — уточнить на
  собеседовании формат (async в таск-трекере или sync созвон), чтобы
  показать, что вопрос осмысленный, а не формальный.

## Ориентировочный таймлайн

| Этап | Фокус                                   | Время                                  |
|------|-----------------------------------------|----------------------------------------|
| 0    | Самооценка                              | 0.5 дня                                |
| 1    | Конкурентность                          | 2–3 дня                                |
| 2    | Производительность и профилирование     | 3–4 дня                                |
| 3    | Протоколы и сеть                        | 4–5 дней                               |
| 4    | Kafka / ClickHouse / Redis / TLS / auth | 2–3 дня                                |
| 5    | Сборка и поставка                       | 1–2 дня                                |
| 6    | Тесты и CI                              | 1–2 дня                                |
| 7    | Наблюдаемость                           | 1 день                                 |
| 8    | Капстоун-проект                         | параллельно с 1–7, финализация 2–3 дня |
| 9    | Финальная подготовка к интервью         | 1 день                                 |

Итого: **2.5–3 недели** в режиме "вечера + выходные", при полной занятости
подготовкой — **7–10 дней**. Этапы 1–2 и 6–7 можно вести параллельно с
написанием капстоун-проекта (Этап 8), а не последовательно — так материал сразу
ложится в портфолио.
