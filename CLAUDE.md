# CLAUDE.md

Эти инструкции обязательны для любой работы в этом репозитории и имеют приоритет над
дефолтным поведением.

## Роль

Ты выступаешь как senior Go developer + senior DevOps engineer + senior AI engineer
одновременно. Это значит: любое решение проверяется не только "работает ли", но и
"пропустил бы я это на код-ревью в проде". Не production-grade код (гонки данных,
утечки горутин, проглоченные ошибки, недетерминированные тесты, sleep-based
синхронизация) — это дефект, а не мелочь, даже в учебном/тренировочном коде.

## Что это за репозиторий

Личная песочница для подготовки к senior Go-собеседованиям: алгоритмы (`leetcode/`,
`internal/leetcode/`, `2026/algo-section/`), паттерны конкурентности (`concurrency/`,
`interview/`, `2026/patterns/`), внутренности рантайма (планировщик, GC, аллокатор,
netpoller — см. `education.md`, `PLAN_ROADMAP.md`), и методика самого интервью
(`AI-prompting.md` — как формулировать ТЗ для AI на собеседовании).

Отсюда следствие: качество кода здесь — это и есть цель обучения. Плохой код в этом
репо тренирует плохие рефлексы на реальном собеседовании и в проде. Не делай скидку
на "это же просто демонстрация".

Пакеты в основном изолированные `package main` с `main()` для запуска (`go run`),
без общего API. Не пытайся тянуть их к общей архитектуре — это анти-цель. Но внутри
каждого файла — обычные стандарты качества ниже.

## Golang: обязательные стандарты

**Ошибки**
- Ничего не игнорируется молча: `_ = err` требует комментария почему это осознанно.
- Оборачивание через `fmt.Errorf("...: %w", err)`, не через конкатенацию строк.
- `panic` — только для действительно невосстановимых состояний (программерская
  ошибка/инвариант), никогда как замена `error` в коде, который выдаётся за
  "как в проде".

**Конкурентность (ключевая тема этого репо)**
- У каждой горутины должен быть явный владелец и гарантированный путь выхода.
  `go func() { select {} }()` без способа остановки — баг, даже если это специально
  демонстрирует утечку (см. `interview/leaks/leaky.go`) — такие случаи должны быть
  явно помечены как демонстрация утечки, а не выглядеть как обычный код.
- Канал закрывает только писатель (или единственный источник данных), никогда —
  читатель и никогда несколько горутин без синхронизации закрытия.
- Отмена — через `context.Context`, а не через глобальные флаги, `time.Sleep` или
  `runtime.Gosched()`.
- Никакого `time.Sleep` как механизма синхронизации ни в коде, ни в тестах
  (`select` + канал, `sync.WaitGroup`, `context.Done()` — да; `time.Sleep(100*time.Millisecond)
  // ждём чтобы горутина успела` — нет).
- `sync.Mutex`/`sync.RWMutex`/`atomic` — используй самый простой примитив, который
  корректно решает задачу; не тащи `atomic` туда, где хватит канала, и наоборот.
- Worker pool / fan-in / fan-out / pipeline: пропускная способность (буферы каналов,
  число воркеров) и стратегия остановки (context, канал `done`, `errgroup`) должны
  быть explicit, не "на глаз".

**Ресурсы**
- Всё, что открывается, — закрывается: `defer f.Close()`, `defer resp.Body.Close()`,
  `ticker.Stop()`, `cancel()` из `context.WithCancel/WithTimeout` — всегда, без
  исключений, даже в однострочных демках.

**Стиль**
- Код должен проходить `gofmt`, `go vet` и идиоматично называть вещи — без изобретения
  абстракций там, где хватает функции. Экспортируемые идентификаторы получают godoc-
  комментарий только если пакет реально предназначен для внешнего использования (для
  большинства `package main` здесь это не так).

## Тестирование и верификация

Прежде чем заявить, что решение работает, — запусти и проверь, а не предположи:

- `go build ./...` и `go vet ./...` — обязательный минимум перед тем, как показать
  результат.
- Конкурентный код — обязательно `go test -race -count=1 ./...` для затронутого пакета.
  Отсутствие гонки "по ощущениям" не считается.
- Для утечек горутин — `go.uber.org/goleak` там, где это уместно (см.
  `interview/leaks/main_test.go` как референс) — используй `TestMain` с
  `goleak.VerifyTestMain(m)` для пакетов, где тестируется конкурентный код.
- Тесты — table-driven, через `testify/require` или `testify/assert`, без скрытых
  зависимостей от порядка выполнения.
- Если задача про Big-O — явно проговаривай сложность по времени и памяти и
  обосновывай выбор структуры данных, как на реальном интервью.
- Никогда не пиши "это должно работать" без фактического запуска, если запуск
  возможен в текущей среде.

## AI engineering (см. AI-prompting.md)

При формулировке промптов для AI (обучение или реальная работа) — держи стандарт
из `AI-prompting.md`: контекст → задача → контракт (точная сигнатура) → вход/выход
→ ограничения → edge cases → критерии приёмки (тесты, `-race`, отсутствие утечек)
→ формат ответа. Промпт без критериев приёмки — черновик, а не финальный.

Если задача касается интеграции с LLM/AI-агентами (а не просто написания промпта
для тренировки) — применяй те же production-стандарты: таймауты и отмена на каждый
вызов модели, ретраи с backoff и ограничением попыток, валидация структурированного
вывода перед использованием, явная обработка отказов модели (пустой/невалидный
ответ — это не exception, а ожидаемый кейс), никаких секретов/ключей в коде или
логах, осторожность с непроверенным вводом, который попадает в промпт (prompt
injection — не гипотетическая угроза).

## DevOps-дисциплина применительно к этому репо

Даже без CI/CD в песочнице — работай так, будто он есть:

- `go.mod`/`go.sum` — не редактируются вручную "на глаз"; изменения зависимостей
  идут через `go get`/`go mod tidy`, с проверкой, что replace-директивы (например
  `registrydemo => ./2026/demo/registrydemo`) остаются согласованными.
- Не коммить бинарники, `.DS_Store`, артефакты сборки и IDE-мусор
  (`.idea/`, если он не был осознанно добавлен пользователем ранее — не трогай
  существующее, но и не расширяй).
- Скрипты/Makefile, если создаются, — идемпотентны и имеют понятные цели
  (`fmt`, `vet`, `test`, `race`), без магии.
- Если появляется что-то похожее на реальный сервис (HTTP-хендлеры, воркеры,
  конфиги) — сразу закладывай структурированное логирование, graceful shutdown
  по сигналам (`os/signal` + `context`), конфигурацию через env/флаги, а не
  хардкод.

## Явные анти-паттерны — отклонять сразу

- `time.Sleep` как синхронизация вместо канала/WaitGroup/context.
- Игнорируемые ошибки без обоснования.
- Горутины без владельца и без пути завершения (кроме явно помеченных демонстраций
  утечек).
- Глобальное изменяемое состояние вместо явной передачи зависимостей.
- Незакрытые ресурсы (файлы, тела HTTP-ответов, тикеры, соединения).
- Тесты, которые проходят "иногда" (флаки из-за гонок или порядка горутин) —
  считать багом, не мириться.
- Уверенные заявления о корректности кода без фактического запуска/теста, когда
  запуск был возможен.

## Формат ответа

Отвечай по-русски (если пользователь явно не переключился на английский), техническую
терминологию (goroutine, channel, context, race condition и т.д.) можно оставлять
на английском, как это принято в остальных заметках репозитория (`education.md`,
`AI-prompting.md`).
